# Unattended channel and Gmail recovery

Release the Deft Host service-fetch route before this Runtime. No database migration or new operator secret is needed. Existing until-revoked account consent and the operator-configured service credential are the durable opt-in; the legacy renewal SID field stores a service-registration provenance label, while current human membership/role, deployment admission, installation, account grant and reviewed bindings remain live requirements. Finite permissions and per-version registration changes retain their existing review/expiry behavior; this work never extends a finite permission or carries a grant across an unreviewed update.

The design reuses current authority resolution and authenticated Host-to-Runtime delivery. An independent enrollment database would duplicate those checks and need a migration; extending bearer expiry would still fail after sufficiently long downtime. The service route accepts only the configured registration, authenticates its authority-channel credential, derives the installation from the Host, and requires owner=operator and current durable consent. No prior technical session row is needed. It cannot choose another owner or create a grant. The existing installer APIs remain compatible.

Renewal begins 5–6 minutes before a technical lease ends. Claims remain closed while lease authority is uncertain. Expired or denied leases trigger service reconciliation for operator-configured registrations. The Runtime retries transient failures indefinitely with exponential jitter (about one second, capped at five minutes), independent of the expired lease. A service-authentication/permission denial emits `reconnect_required`; a later valid owner installation resets recovery. Installation ACKs contain identifiers only. The encrypted installed-channel journal is authoritative after lost ACKs and restart. Superseded workers stop; no start, result, provider effect or Send operation is replayed.

Gmail refresh is serialized by the existing account custody lock. Encrypted `refresh_reconciliation` records distinguish `transport_unavailable` and `verification_pending`, with a durable next retry time. A received token response is committed before post-request authority checks and identity GETs. Safe retries retain the newest credentials; missing replacement refresh tokens retain the prior token. Legacy Gmail `refresh_pending` rows become eligible for reconciliation. The public account remains a connected grant while token access is pending; no token is returned until identity and live authority checks succeed. Actual `invalid_grant`, identity mismatch and removed required scope require reconnect. Microsoft lost rotating-token responses retain their uncertain-outcome fence.

The writer's `.writer-lock.sqlite` contains no application data. A lifetime `BEGIN EXCLUSIVE` transaction holds the OS file lock on supported local filesystems, including across containers sharing the same filesystem. Crashes release the lock; an active writer cannot be displaced by a TTL or recycled PID. Application row encryption, fsync/atomic rename, revision CAS and Send journals are unchanged. Preserve the SQLite lock file path/inode while any writer runs. Existing private-root and unsupported-network-filesystem checks remain in force. Windows remains a local fixture mode, with the existing durability limitation.

Regression coverage includes extended Host/Runtime outage, stale local metadata, renewal/install ACK loss, transient/permanent service failure, concurrent refresh, refresh/verification timeout, persisted-token restart, legacy pending state, invalid_grant, live revocation, hard kill around read/commit and second-writer exclusion. All use synthetic providers; they do not establish a live Gmail or deployment result.
