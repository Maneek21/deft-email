# Unattended channel and Gmail recovery

Runtime20 pairs with Host132 for retained reattachment. Each phase is bounded at120seconds and clipped by the current Host request, review, account and action deadlines. Every live authority and effect fence remains; ordinary HTTP/data/effect budgets stay30seconds and short Runtime channel leases stay15minutes. This fixes the preview.21 multi-purpose phase-budget failure. An expired trusted issuance can authorize only current read-only status reconciliation, never a late activation or a new permission. No recovery or renewal retries a provider effect or sends mail.

Release the Deft Host service-fetch route before this Runtime. No database migration or new operator secret is needed. Existing until-revoked account consent and the operator-configured service credential are the durable opt-in; the legacy renewal SID field stores a service-registration provenance label, while current human membership/role, deployment admission, installation, account grant and reviewed bindings remain live requirements. Finite permissions and per-version registration changes retain their existing review/expiry behavior; this work never extends a finite permission or carries a grant across an unreviewed update.

The design reuses current authority resolution and authenticated Host-to-Runtime delivery. An independent enrollment database would duplicate those checks and need a migration; extending bearer expiry would still fail after sufficiently long downtime. The service route accepts only the configured registration, authenticates its authority-channel credential, derives the installation from the Host, and requires owner=operator and current durable consent. No prior technical session row is needed. It cannot choose another owner or create a grant. The existing installer APIs remain compatible.

Renewal begins 5–6 minutes before a technical lease ends. Claims remain closed while lease authority is uncertain. Expired or denied leases trigger service reconciliation for operator-configured registrations. The Runtime retries transient failures indefinitely with exponential jitter (about one second, capped at five minutes), independent of the expired lease. A service-authentication/permission denial emits `reconnect_required`; a later valid owner installation resets recovery. Installation ACKs contain identifiers only. The encrypted installed-channel journal is authoritative after lost ACKs and restart. Superseded workers stop; no start, result, provider effect or Send operation is replayed.

Gmail refresh is serialized by the existing account custody lock. Encrypted `refresh_reconciliation` records distinguish `transport_unavailable` and `verification_pending`, with a durable next retry time. A received token response is committed before post-request authority checks and identity GETs. Safe retries retain the newest credentials; missing replacement refresh tokens retain the prior token. Legacy Gmail `refresh_pending` rows become eligible for reconciliation only through operational read custody; upgrade and credential-repair readers retain the original pending fence. The public account remains a connected grant while token access is pending; no token is returned until identity and live authority checks succeed. Actual `invalid_grant`, identity mismatch and removed required scope require reconnect. Microsoft lost rotating-token responses retain their uncertain-outcome fence.

The writer's `.writer-lock.sqlite` contains no application data. A lifetime `BEGIN EXCLUSIVE` transaction holds the OS file lock on supported local filesystems, including across containers sharing the same filesystem. New writers create no .writer marker; crashes during bootstrap, read or commit release the lock. An active writer cannot be displaced by a TTL or recycled PID. Application row encryption, fsync/atomic rename, revision CAS and Send journals are unchanged. Preserve the SQLite lock file path/inode while any writer runs. Existing private-root and unsupported-network-filesystem checks remain in force. Windows remains a local fixture mode, with the existing durability limitation.

Regression coverage includes extended Host/Runtime outage, stale local metadata, renewal/install ACK loss, transient/permanent service failure, concurrent refresh, refresh/verification timeout, persisted-token restart, legacy pending state, invalid_grant, live revocation, hard kill around read/commit and second-writer exclusion. All use synthetic providers; they do not establish a live Gmail or deployment result.

Host preview.131 or newer is required. Trusted App upgrades create fresh version-bound registration IDs. The Runtime accepts such a successor only through v2 reattachment from a previously enrolled source, after the authenticated Host authority and existing exact custody/purpose checks succeed. A durable prepared-transition index precedes the prepare ACK; a connected journal and exact receipt enroll the successor. Restart reconstructs that routing enrollment, including activation whose ACK was lost. The service supervisor nominates this current registration, preserving the Host service endpoint's exact-ID fence. Channel installation, data access and service reacquisition use the enrolled current registration without operator-file edits. This routing state never replaces live Host authorization, extends finite permissions, or retries provider effects.
